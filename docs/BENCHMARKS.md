# Benchmarks

This document records what was measured, on what machine, how, and what the numbers do and do not
mean. Every figure here is reproducible from the repository — the harnesses are in `bench/` and the
corpus generator is in `scripts/`.

## Test machine

| | |
|---|---|
| CPU | 8 vCPU, shared cloud container |
| OS | Linux (Ubuntu 24.04 base), 6.x kernel |
| Compiler | `g++ 13.3.0`, `-std=c++20 -O2`, LTO enabled |
| Build | `tessera 1.0.0`, release |
| Storage | network-backed container volume |
| Page cache | warm (each file read at least once before timing) |

**Read the caveats.** This is a shared container, not a tuned workstation, and the numbers are
single-run. They are honest, not best-case, and they are in the same ballpark as desktop hardware for
this workload because the bottleneck is memory bandwidth and page-cache reads, not CPU generation.
Your laptop with NVMe and a warm cache will be faster; a cold cache will be slower until the OS has
read the file once.

## Corpus

Generated by [`scripts/gen_data.py`](../scripts/gen_data.py) with a fixed seed, so the files are
byte-identical for anyone who runs the generator.

| File | Rows | Bytes | Columns | Format |
|---|---:|---:|---:|---|
| `orders10m.csv` | 10,000,000 | 1,171,499,154 (1.09 GiB) | 13 | comma, header |
| `events4m.jsonl` | 4,000,000 | 940,375,307 (897 MiB) | 9 (union of keys) | JSON Lines |
| `orders2m.tsv` | 2,000,000 | 234,302,320 (223 MiB) | 13 | tab, header |

The generator deliberately produces the awkward cases that break naive parsers: quoted commas,
doubled quotes inside quoted fields, **embedded newlines inside quoted values**, empty cells, padded
strings, and a handful of columns that look numeric but are not.

```sh
python3 scripts/gen_data.py --rows 10000000 --out bench/orders10m.csv
python3 scripts/gen_data.py --rows 4000000 --format jsonl --out bench/events4m.jsonl
python3 scripts/gen_data.py --rows 2000000 --format tsv --out bench/orders2m.tsv
```

## Method

Timing uses three independent tools so no single one can flatter the result:

* `tessera bench <file>` — the tool's own instrumented timing of open, scan, filter and sort, with
  throughput computed from the actual byte and row counts. It also prints a checksum of the scanned
  bytes, so a "scan" that silently optimised itself away would be visible.
* `bench/measure.py` — `fork` + `wait4`, measuring wall time and `ru_maxrss` per child process, so
  each command's peak is attributed to that command rather than to the whole session.
* `bench/measure_anon.sh` — samples `/proc/<pid>/status` while the process runs, separating peak
  **anonymous** memory (`RssAnon`, the program's own allocations) from peak **file-backed** memory
  (`RssFile`, mapped pages that the OS may evict).

## Results

### Open, inspect, profile

| Operation | Wall | Detail |
|---|---:|---|
| Open + index `orders10m.csv` | **0.911 s** | 1.29 GB/s · 11.0 M rows/s · 76.3 MB index |
| `info` (open + detect + infer) | **1.078 s** | 0.972 s on the immediate second run |
| `info` after `tessera index` | **0.170 s** | sidecar `.tessera.idx`, 12.4 MB |
| `head -n 5` with sidecar | **0.164 s** | independent of file size |
| Full scan + checksum | **0.073 s** | 14.89 GB/s · 136.5 M rows/s |
| `info` `events4m.jsonl` | **6.786 s** | record indexing, union-of-keys schema detection |
| `info` `orders2m.tsv` | **0.539 s** | |
| `stats` full profile, `events4m.jsonl` | **12.034 s** | fill rate, quantiles, histogram, top values, HLL distinct |

### Query and export

| Query on `orders10m.csv` | Wall | Notes |
|---|---:|---|
| `SELECT count(*) FROM t` | **1.390 s** | 0.911 s of it is the open; 0.48 s to count 10M rows |
| `WHERE units > 36` | **0.790 s** | 999,814 matches · 12.7 M rows/s |
| `ORDER BY created_at` over 1,000,000 rows | **1.303 s** | |
| `GROUP BY region` + `sum(revenue)` + `ORDER BY` | **4.963 s** | 5 groups, full scan |
| `SELECT … WHERE status='failed' ORDER BY revenue DESC LIMIT 10` | **4.681 s** | full scan, sort, top-10 |
| Export 999,814 matching rows to CSV | **4.438 s** | 1.0 M rows written |

Note that every query figure *includes* the open. A second query in the same session, or a reopen
with the sidecar present, starts from 0.17 s.

### Memory

| Operation | Peak anonymous | Peak file-backed (reclaimable) |
|---|---:|---:|
| `info` `orders10m.csv` (1.09 GiB) | **184 MB** | 1,121 MB |
| `info` `events4m.jsonl` (897 MiB) | **556 MB** | 899 MB |
| `info` `orders2m.tsv` (223 MiB) | **34 MB** | 227 MB |

The index is 8 bytes per row: 76.3 MB for ten million rows. The gap between that and 184 MB peak is
the growth overhead of the offsets vector while it is being built, plus detection and inference
buffers. The file-backed column is the mapping — the operating system's page cache, which it will
reclaim under pressure and re-read from disk on demand. That is why opening a 1.09 GiB file does not
require 1.09 GiB of free RAM in any meaningful sense.

### Baselines, measured on the same file and machine

| Approach | Time to be queryable | Peak RSS |
|---|---:|---:|
| `python csv.reader` into a list of lists | 56.96 s | 8.02 GB |
| `pandas.read_csv` 3.0.5 (`low_memory=False`) | 34.84 s | 5.36 GB |
| … then `.groupby("region")["revenue"].sum()` | +0.89 s (35.74 s total) | 5.36 GB |
| **Tessera** `info` | **1.08 s** | **184 MB** |
| **Tessera** same `GROUP BY region` + `sum` | **4.96 s** | **184 MB** |

Run them yourself:

```sh
python3 bench/baseline.py bench/orders10m.csv            # stdlib
python3 bench/baseline_pandas.py bench/orders10m.csv     # pandas
```

### Correctness cross-check

Speed claims are only interesting if the answer is right. On the same 10,000,000 rows:

| `region` | Tessera `sum(revenue)` | pandas `sum` (7 s.f.) |
|---|---:|---:|
| LATAM | 21,463,054,623 | 2.146305e10 |
| US | 21,429,415,811.2 | 2.142942e10 |
| EU | 21,414,050,958.2 | 2.141405e10 |
| MEA | 21,406,652,189.7 | 2.140665e10 |
| APAC | 21,394,233,345.4 | 2.139423e10 |

The totals agree to seven significant digits; the remaining difference is float64 summation order,
which differs because Tessera sums in file order per group while pandas sums over columnar blocks.

## What the numbers do not say

* **Not a database benchmark.** Tessera has no joins, no indexes beyond row offsets, and no cost
  model. DuckDB will beat it on complex analytical queries and is the right tool for those. The
  comparison here is against the thing people actually do first — get the file open and look at it.
* **Single-run, shared hardware.** Variance of ±10% between runs is normal on this container. The
  ordering of results is stable; the third digit is not.
* **Warm cache.** A cold first read is disk-bound, not CPU-bound, and no tool can avoid that.
* **JSONL is expensive.** 897 MiB of JSON Lines takes 6.8 s to index versus 1.08 s for a comparable
  CSV, because every record must be scanned twice (once to find its extent, once to extract the key
  union). It is still one pass of memory bandwidth, but it is a genuinely heavier format, and the
  numbers say so rather than pretending otherwise.
* **Sorting is in memory.** `ORDER BY` over a billion rows is a database's job; Tessera will use the
  RAM it needs and should not be used to sort files larger than memory.

## Reproducing everything

```sh
# 1. corpus
python3 scripts/gen_data.py --rows 10000000 --out bench/orders10m.csv
python3 scripts/gen_data.py --rows 4000000 --format jsonl --out bench/events4m.jsonl
python3 scripts/gen_data.py --rows 2000000 --format tsv --out bench/orders2m.tsv

# 2. the tool's own instrumented timings
./build/tessera bench bench/orders10m.csv

# 3. wall time + peak RSS per command
python3 bench/measure.py

# 4. anonymous vs file-backed memory
bash bench/measure_anon.sh

# 5. the baselines
python3 bench/baseline.py bench/orders10m.csv
python3 bench/baseline_pandas.py bench/orders10m.csv
```
